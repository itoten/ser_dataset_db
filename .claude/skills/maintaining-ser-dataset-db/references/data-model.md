# Data model and rules

The authoritative definitions are `schema/columns.csv` (every column, its type and allowed
nulls), `schema/enums.csv` (every allowed value) and `schema/tables.csv` (keys). The README and
`docs/manual.md` explain the design. This file condenses the rules that matter while editing.

## Tables

| File | One row is | Key |
|---|---|---|
| `data/datasets.csv` | one dataset (the central table) | `dataset_id` |
| `data/evidence.csv` | the source of one value of a `datasets` cell, or of an attribute of a label set | `evidence_id` = `<dataset_id>/<field>/<NN>` |
| `data/sources.csv` | one source document | `source_id` |
| `data/dataset_sources.csv` | a source that introduces a dataset, with its role | `dataset_id`, `source_id`, `role` |
| `data/annotations.csv` | a label set or another annotation of a dataset, with its own source | `dataset_id`, `item`, `name` |
| `data/label_counts.csv` | files per label of a label set, from a source | `dataset_id`, `item`, `label`, `source_id` |
| `data/issues.csv` | one problem of a release as distributed | `dataset_id`, `issue_no` |
| `data/aliases.csv` | another name of a dataset | `dataset_id`, `alias` |
| `data/relations.csv` | a relation between two datasets | `dataset_id`, `relation`, `other_dataset_id` |
| `data/label_normalization.csv` | spelling and word-form variants of label names | `source_label` |
| `views/*.csv` | generated by `tools/views.py`; never edit by hand | none |

Dataset IDs match `^[a-z][a-z0-9]*(_[a-z0-9]+)*$`; an implemented dataset's ID equals its recipe
name. Committed IDs never change; if one must, keep the old ID as an alias of type `former_label`.

## Missing values

Five different meanings. Never mix them.

| Written as | Means |
|---|---|
| (empty) | not checked yet |
| `unknown` | checked, but the sources do not say or it cannot be decided |
| `NA` | does not apply |
| `none` | checked, and there is none |
| `conflicting` | sources disagree (set by the rows, see below) |

Which of them a column accepts is in the `nulls` column of `schema/columns.csv`. Licenses also
have `none_stated` (no license statement found). Multi-valued cells use `;` as separator.

## Sources and evidence rows

Columns with `evidence=yes` in `schema/columns.csv` need an evidence row for their value. The
attributes `annotator`, `label_basis` and `label_verification` of every label set
(`emotion_categories`, `emotion_attributes`, `speaking_style`, `sentiment`, `intent`) have evidence rows whose `field` is
`<item>.<attribute>` (for example `emotion_categories.label_basis`).

A source (`sources.csv`) has a `kind` (paper, distribution_page, dataset_card, license_file,
release_files, readme, mirror, survey, other), a `publisher` and the `source_type` that goes
with it:

| source_type | publisher | meaning |
|---|---|---|
| `primary` | authors | published by the dataset's authors or their organisation: paper, page, license file, release files |
| `implementation` | recipe_author | `## The data` section of a recipe readme at a commit on the public fork; what only opening the release shows. A practical reference, not a research result |
| `secondary` | third_party | mirror, re-upload, survey, database; only when the primary source cannot be accessed. `kind` is `mirror` or `survey` |

`source_id` is `<dataset_id>_<kind>` (`aesdd_page`, `aesdd_paper`, `aesdd_card`, `aesdd_readme`;
`_2` for a second one) for a source of one dataset, and a short name for a shared one. A source
is identified by URL (arXiv without versions, `https://`, no trailing slash) or DOI; the same
URL is a second source when cited with another `source_type`. `describes_version` says which
release the source describes. `identity_basis` says why the source is about this dataset. A
source with an empty publisher has not been checked yet (the validator warns).

An evidence row has the value, the `source_id`, the `locator` (where in the source, 25 words at
most; for a readme `commit <12 characters>; <heading>`), `checked_on`, `checked_by` (`claude`, or
`user` when the maintainer opened the source) and a `status`.

## Deciding a value

The cell of a `datasets` column is decided by the live rows of its field (`current`,
`conflicting`, `provisional`):

| Rows | The cell is |
|---|---|
| `current` rows, all with the same value | that value |
| two or more `conflicting` rows with different values | `conflicting` |
| one `provisional` row only | its value |
| none | empty |

`current` and `conflicting` together, `current` rows that disagree, or `current` next to
`provisional` are errors. A new value: add the row; the old `current` or `provisional` row
becomes `superseded` (`R.ev` does it). A disagreeing source: `R.conflicting` (it turns the
`current` rows into `conflicting`). A dispute settled by a source: `R.resolve`, then `R.ev`.
A `provisional` row has no source (`source_id` and `locator` empty) and a note starting with
`Provisional:`; it is a value from earlier records without a source. It is resolved by a source or removed; never add a new one. Never delete
rows; history is part of the record.

## Label sets and annotations

A label set is an `annotations` row whose `item` equals its `name`: `emotion_categories`
(categorical emotion), `emotion_attributes` (dimensional: arousal, valence, ...),
`speaking_style`, `sentiment`, `intent`. It has `labels` (the source's own words,
`;`-separated, `unknown`/`none` allowed), `scale` (how the source describes the granularity),
`perceived_from` (what listeners saw or heard), and `annotator`, `label_basis`,
`label_verification`. Never infer one of these from another: acted speech can carry perceived
labels.

- `annotator`: `human`, `automatic`, `mixed`, `synthesis_specified`.
- `label_basis`: `intended` (the emotion the speaker was told to portray), `perceived`,
  `self_reported`, `context_inferred`, `automatic`; one per set (two only when a single label field
  mixes them, as in DailyTalk and NonverbalTTS).
- `label_verification`: `human_reviewed`, `listener_validated` (instructed labels confirmed by a
  listening test), `none`, `unknown`, `NA`.

The datasets columns `emotion_categories`, `emotion_attributes`, `main_label_set_type`,
`main_labels`, `label_source`, `label_basis`, `label_verification` are derived from the main set
(`emotion_categories`, else `emotion_attributes`, else another set) by `tools/derive.py`; do not
edit them. `R.save()` recomputes them.

Each label set has one `label_basis`. When a release has separate labels for another basis (for example
the actors' intended emotion and the listeners' perceived emotion), the main set keeps one basis and the
other is a further row with `name` = `<basis>_<item>` (`perceived_emotion_categories`) and its own
`annotator`, `label_basis`, `label_verification`; its evidence fields are `<name>.<attribute>`. Perceived
ratings that are not category labels stay `listener_ratings` rows.

Other annotations use the fixed `item` vocabulary (`schema/enums.csv` annotation_item) and keep
the release's own name in `name`: `speaker_id`, `speaker_gender`, `transcript`, `sentence_id`,
`session_id`, `take`, `intensity`, `listener_ratings`, `listening_test`, `segmentation`,
`acoustic_features`, `split`, `video`, `physiological`, ..., `other`. Each row has its own
source; a row without one has a note starting with `Provisional:`.

`label_counts.csv` holds the number of files per label of a label set, in the source's own label
words, from the documentation (`primary`) or the recipe readme (`implementation`). Both can exist
for one label; they do not have to agree. `label_normalization.csv` maps only spelling (case,
spaces) and word forms (angry/anger); a mapping that changes the meaning (joy to happy) does not
belong in the DB.

## Counts: documentation versus release

`n_files_reported`, `hours_reported`, `n_speakers_reported` are what the documentation says.
`n_files_release`, `hours_release`, `n_speakers_release` are the whole release as distributed,
before any filtering, from the recipe readme (`implementation`). Both are recorded; they often
differ (versions, rounding, files left out by the authors) and the DB does not choose. Counts
after a recipe's own filtering or splitting are not recorded. `access_method` is what the
documentation says about obtaining the data; `access_observed` (with `access_observed_on`) is
what happened when the data was requested or downloaded (`obtained`, or one of the
`access_method` values).

## How the audio was produced, where it comes from, how the labels were made

- `speech_production` (`;`-separated): `acted` (an instructed emotion was portrayed, including
  film and drama), `improvised` (acted without a script), `elicited` (induced by stimuli, tasks
  or a conversation set-up), `spontaneous`, `read` (without an emotion instruction), `synthetic`.
- `material_origin` (`;`-separated): `recorded_for_dataset`, `film_tv`, `web_video`, `podcast`,
  `broadcast`, `synthetic`, `multiple`, `other`. For third-party material, what the sources say
  about the rights is quoted in `source_rights_note`; the DB gives no verdict.
- `vocal_content`: `speech`, `nonverbal`, `speech_and_nonverbal`, `unknown`.
- `spoken_text_design` (`;`-separated when the data mixes designs): `parallel` (the same
  sentences in every emotion), `neutral_text`, `emotion_specific_text`, `unrelated_text`,
  `dialogue_script`, `unscripted`. Record it from a design statement or the readme, never by
  guessing; do not add a judgement of how far the words give the label away. Datasets that share
  sentences with another dataset are linked by the `shares_sentences_with` relation, only when a
  source states it.
- `listening_test`: `reported` or `not_stated`; results stay in the source.
- `official_split`: `true` when a source says the release comes with a partition into train/dev/test or similar, `false` when a source says it does not; empty when no source says. The split itself stays in the source.

## Issues

One row per problem of the release as distributed, with a `type` (`corrupt_or_unreadable`,
`duplicate`, `missing_or_mismatched_label`, `differs_from_documentation`,
`silent_or_non_speech`, `unusual_audio`, `listening_observation`, `other`), the source's wording
in `description`, `n` if given, and the readme location. A `listening_observation` starts with
"Observation by the recipe author (date)" and says what was heard.

## What counts as one dataset

One row per original (first published) dataset. Plain re-uploads are aliases and mirror sources.
Datasets whose content differs from the original (re-splits, subsets, new labels) are separate
rows linked by `relations` (`version_of`, `subset_of`, `contains`, `distinct_from`,
`possibly_same_as`, `shares_sentences_with`). A version that the authors publish under another
name or DOI is a row of its own (`version_of`); other versions are one row and the sources'
`describes_version` says which release each describes. When two rows turn out to be the same,
link them with `possibly_same_as`; IDs are never deleted.

## Writing free text

Facts and caveats only, in English, each naming its source (`[aesdd_page]`). No advice ("should
not be used"), no judgement ("poor data"), no personal names, no machine-specific paths.
Quotations keep their original language.
