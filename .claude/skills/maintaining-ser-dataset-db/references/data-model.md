# Data model and rules

The authoritative definitions are `schema/columns.csv` (every column, its type and allowed
nulls), `schema/enums.csv` (every allowed value) and `schema/tables.csv` (keys). The README and
`docs/manual.md` explain the design. This file condenses the rules that matter while editing.

## Tables

| File | One row is | Key |
|---|---|---|
| `data/datasets.csv` | one dataset (the central table) | `dataset_id` |
| `data/evidence.csv` | the source for one value of a `datasets` cell | `evidence_id` = `<dataset_id>/<field>/<NN>` |
| `data/aliases.csv` | another name of a dataset | `dataset_id`, `alias` |
| `data/relations.csv` | a relation between two datasets | `dataset_id`, `relation`, `other_dataset_id` |
| `data/recipes.csv` | one toolkit recipe (implemented datasets only) | `recipe` |
| `data/recipe_labels.csv` | one label of one recipe | `recipe`, `label` |
| `data/annotations.csv` | one non-emotion annotation of a dataset, with its own source | `dataset_id`, `item` |
| `data/benchmark_membership.csv` | one member recipe of a multi-corpus recipe | `benchmark_recipe`, `member_recipe`, `role` |
| `measurements/<recipe>.json` | measured counts of the recipe's built data (written by `tools/measure.py`) | file name |
| `views/*.csv` | generated by `tools/views.py`; never edit by hand | — |

Dataset IDs match `^[a-z][a-z0-9]*(_[a-z0-9]+)*$`; an implemented dataset's ID equals its recipe
name. Committed IDs never change; if one must, keep the old ID as an alias of type `former_label`.

## Missing values

Four different meanings. Never mix them.

| Written as | Means |
|---|---|
| (empty) | not checked yet |
| `unknown` | checked, but the sources do not say or it cannot be decided |
| `NA` | does not apply |
| `none` | checked, and there is none |

Which of them a column accepts is in the `nulls` column of `schema/columns.csv`. Licenses also
have `none_stated` (no license statement found). Multi-valued cells use `;` as separator.

## Evidence rows

These `datasets` columns need an evidence row for their value: `languages`,
`recording_context`, `vocal_content`, `license_spdx`, `access_method`, `raw_audio_available`,
`n_utt_reported`, `hours_reported`, `n_speakers_reported`, `n_files_release_measured`,
`n_speakers_measured`, `labels_discrete_reported`, `dimensional_attributes`, `espnet_status`,
`status_reason_codes`, `label_source`, `label_verification`, `speech_production`, `label_basis`,
`text_emotion_link`, `lexical_confound`.

Columns that never take evidence rows (adding one is a validation error): URL columns
(`source_url`, `download_url`, `paper_url`, `doi`) and text columns (`status_note`, `notes`,
`license_note`, `language_note`, `labels_discrete_note`, `annotations_other`, `release_version`,
`report_path`, `n_discrete_labels_reported`).

Rules checked by `tools/validate.py`:
- Each (dataset, field) has exactly one row with `is_canonical=true`, and its value equals the cell.
- When a value changes, the old canonical row stays and becomes `is_canonical=false`,
  `status=superseded`. History is never deleted.
- `source_type`, strongest first: `user` (a decision or check by the project maintainer),
  `measured` (counted or tried by us), `primary` (the authors' paper, official page, LICENSE),
  `project_doc` (an internal note whose source cannot be pinned down), `secondary` (third parties:
  mirrors, surveys, re-uploads), `sheet` (the spreadsheet the DB was originally imported from).
  A weaker source may be canonical only with a `note` explaining why.
- `*_reported` columns never take `measured` evidence; `*_measured` columns take only `measured`.
  Published figures and our own counts live side by side in separate columns.
- `locator` says where in the source the value is (a quote or section, 25 words at most).
  `via` says how we came to it (e.g. the report that pointed us there).
  `checked_by` is `claude`, `user` or `script`.

## Conflicting sources

- Equally strong sources disagree and nothing decides between them: keep two or more rows with
  `status=conflicting` and put `conflicting` in the cell (used for licenses).
- One value can be preferred for a stated reason (a newer release, an arithmetic slip in the
  source, a column that cannot hold `conflicting` such as an integer count): make the preferred
  value canonical, keep each other value as a row with `is_canonical=false`, `status=conflicting`,
  and explain the choice in the notes of both rows.

## Dataset status

`espnet_status`:

| Value | Meaning |
|---|---|
| `implemented` | the toolkit has a recipe and the maintainers keep it. `status_reason_codes=NA`; the dataset has a `recipes.csv` row |
| `candidate` | has audio and labels usable for classification, and can probably be obtained. Not yet considered: reason `unexamined` |
| `needs_decision` | only the maintainers can decide (cost, terms of use, application wording) |
| `deferred` | could not be confirmed yet (the distributor does not answer, the access route is unknown) |
| `excluded` | a clear reason not to use it |

`excluded` needs a clear reason: no audio (text, features, paper or code only), a redistribution
of another corpus or a duplicate row, labels unusable for classification, labels that follow the
spoken text rather than the voice (confirmed by listening and decided by the maintainers), a
regional restriction, or redistribution not allowed.

Never a reason to exclude: size, manual access steps (application, signature, login, payment),
being hosted on Kaggle, the kind of label (polarity, intent, dimensional, speaking style),
automatic labels, synthetic speech. Record such caveats in `status_note` and keep the row a
`candidate`.

Reason codes are the `reason_code` rows of `schema/enums.csv`. If none fits, add one there and
describe it in the exclusion section of `docs/manual.md`.

## Label provenance

- `label_source`: `human`, `automatic`, `mixed` or `synthesis_specified`. Emotions that actors were
  asked to portray are `human`. `synthesis_specified` is for synthetic audio whose label is the
  emotion given to the synthesiser.
- `label_verification`: `human_reviewed` (the source says people checked automatic labels),
  `listener_validated` (instructed labels were confirmed or filtered by a listening test; the
  label itself stays the instructed one), `none` (the source says nobody checked), `unknown`
  (the sources say nothing), `NA` (nothing to check).

## How the audio was produced vs. how the labels were made

These are two independent facts and are recorded in separate columns. Acted speech can carry
perceived labels, and spontaneous speech can carry self-reported ones; never infer one from the
other. Perceived labels are especially valuable, so record them precisely.

| Column | Values (`;`-separated when several apply) |
|---|---|
| `speech_production` | `acted` (speakers portrayed an emotion: instructed portrayals, and scripted film or drama performances), `elicited` (emotion induced by stimuli, tasks or a set-up conversation), `spontaneous` (natural speech: conversations, broadcasts, streams), `read` (reading without an emotion instruction), `synthetic` |
| `label_basis` | `intended` (the emotion the speaker was told to portray), `perceived` (what listeners or raters judged), `self_reported` (the speaker's own report), `context_inferred` (from the scene, script or the meaning of the words), `automatic` (a model); `none` if there are no emotion labels |
| `label_basis_note` (free text) | number of raters per clip, what raters saw or heard (audio only, video, transcript), how ratings were combined (majority, mean, consensus), which label set is the main one, listening-test details |
| `recipes.label_basis_used` | which kind of label the recipe actually trains on, for datasets that ship more than one |

`recording_context` keeps the setting or medium (studio, YouTube, TV, film). Fill all of these
from the paper or official documentation of the dataset, with evidence rows; when the sources
are silent, write `unknown` and say so in the note.

## Text and labels (shortcut risk)

If the words spoken give the label away, a model can learn the words instead of the voice.
Data whose labels follow only the words is excluded (`labels_from_text_content`); data with real
paralinguistic information plus some word correlation is flagged with these columns, so that
someone checks the actual data before relying on it.

| Column | Values |
|---|---|
| `text_emotion_link` (`;`-separated) | `parallel` (same sentences in every emotion), `neutral_text` (semantically neutral sentences), `emotion_specific_text` (content matches the emotion), `unrelated_text` (sentences assigned without regard to the emotion), `dialogue_script` (film, drama or written-dialogue lines), `unscripted` |
| `lexical_confound` | `full` (each sentence under one emotion only), `strong` (most utterances), `moderate` (a substantial part), `weak` (a small part), `possible` (a documented reason to suspect it, such as unscripted speech or labels assigned with the transcript visible), `none` (ruled out by design: parallel, neutral or emotion-independent text, or no words) |
| `lexical_confound_note` (free text) | what the value rests on and its scope |

- Fill a value only from a design statement in the paper or official documentation, or from a
  measurement (count the emotions each sentence occurs under, from transcripts). Never guess.
  Measuring is optional because it can be costly: if the sources are silent and no cheap check
  exists, write `unknown` (checked, the sources do not say) and, with a documented reason to
  suspect a correlation, `lexical_confound=possible`. Leave a cell empty only if the dataset
  was not looked at.
- Prefer flagging: anything with a documented chance of correlation gets `possible` or above.
  `none` needs a design that rules it out.
- Sentence numbers in file names do not prove that the same text was read in every emotion:
  transcribe a sample. Whisper output is a measurement, but note that no person checked it.
  Keep the outputs under `measurements/text_link/`.

## Annotations

Record every annotation besides the main emotion label, one row per item: speaker ID, gender,
age, language, sentence or prompt ID, take number, transcript, device, recording position,
quality scores, and so on. `annotator` is `human`, `automatic`, `mixed` or `unknown`; `unit` is
`utterance`, `segment`, `word`, `recording`, `conversation`, `speaker` or `dataset`.
`used_in_recipe` may be `true` only for implemented datasets (use `NA` otherwise). When the
sources do not say who made an annotation, write `unknown`, or say in `note` that it is inferred.

## Recipe tables

`recipes.csv` has automatic columns (filled from the recipe branch and `measurements/`) and
hand-written ones:

| Column | Values |
|---|---|
| `report_path` | the recipe's review notes, relative to the directory that contains the repository |
| `official_split_exists` | `true` / `false` |
| `split_method` | `official`, `official_with_carved_valid`, `random_stratified_by_label`, `speaker_independent`, `sentence_independent`, `source_group_independent`, `other` |
| `split_unit`, `recipe_exclusions_note`, `known_issues`, `notes` | free text |
| `speaker_overlap` | `true` / `false` / `unknown` |
| `label_basis_used` | the `label_basis` value(s) of the labels the recipe trains on |
| `baseline_status` | `evaluated`, `trained_only`, `not_run`, `unknown` |

`recipe_labels.csv`: `common7` is one of angry, happy, sad, neutral, fear, disgust, surprise, or
`none` for anything else. `mapping_type` is `identity`, `spelling_fix` (anger → angry),
`synonym_rename` (joy → happy), `outside_common7` or `dropped_by_recipe`. `label_type` is
`categorical`, `polarity`, `intent`, `dimensional` or `other`.

## What counts as one dataset

- One row per original (first published) dataset. A plain re-upload (Hugging Face, Kaggle, a
  mirror) is an alias of the original, not a new row.
- A derivative with different content (subset, re-split, new labels) is its own row, linked with
  `relations` (`version_of`, `subset_of`, `contains`, `distinct_from`, `possibly_same_as`).
  Add a relation only when a source states it; otherwise write the suspicion in `notes`.
- Two rows for the same thing: mark one `excluded` with `duplicate_entry` and link them with
  `possibly_same_as`. Do not delete IDs.
- Datasets without audio stay in the DB as `excluded`, so the check is not repeated later.

## Writing free text

- Write only what a source or a measurement supports. Never invent URLs or titles.
- `notes`: facts about the release (provenance, size, format, files, known defects).
  `status_note`: what is used and what to watch out for, in one or two sentences.
  `license_note`: the gist of the license wording and any disagreement between sources.
- Use absolute dates (2026-01-31), never "today" or "last week".
- Write all text in English. Quote non-English wording only when it matters (e.g. a name or a license sentence), with an English gloss.
