# 2026-10-30: what the status columns should mean

Participants: the project maintainer and Claude (the DB maintenance session). Where things stand now is in [../agenda.md](../agenda.md).

## 1. Trigger: the number of implemented datasets

- The maintainer expected at least 102 implemented datasets; `implemented` counted 95.
- Check: the recipe branch has single-corpus recipes for 102 datasets. Seven were not registered. `multidialog` and `rasa` were waiting for their health checks. `anad`, `audiospeechsentiment`, `bari_emospeech`, `thanushs25_tamil` and `visec` had recipes but were recorded as `deferred`, `excluded` or `needs_decision`.
- The maintainer: whether a recipe exists in ESPnet and whether the data is used are mixed in `espnet_status`; they should be separate.
- The maintainer asked for all seven to be registered as implemented. Six were (commit 1802789). `bari_emospeech` was not, because its corpus had been deleted and must be downloaded again to be measured.
- The maintainer also noted that a question is sometimes only a request for an opinion: the DB is changed only when explicitly asked.

## 2. Proposal of three axes (Claude)

| Axis | Question | Proposed form |
|---|---|---|
| Implementation | Is there a recipe in ESPnet? | No column; derived from whether `recipes.csv` has a row |
| Depth of investigation | How far has the dataset been examined? | not examined / documents only / data |
| Use decision | Is the data used in the research? | undecided / use / evaluation only / on hold / not used |

## 3. General and local information

- The maintainer wants the DB to become a public resource for researchers and students interested in SER. In such a resource, the maintainer's own experiments and the implementation status in a local ESPnet fork would be out of place; local and general information should then be separated clearly.
- For now experiments have priority, and the mix is acceptable as it is.

## 4. `recipes.csv`

- One row per `egs3/<name>/cls` recipe, with columns derived from the recipe branch, columns from measurements, and hand-written columns.
- The manual mentions it in one table row (section 4.2) and has no section describing its columns: a gap.

## 5. The implementation axis

- Claude: whether a recipe exists and whether it was measured can be checked automatically. Health-check results exist only outside the DB (a status log of the health-check runs). Proposal: health-check columns in `recipes.csv`, and an `implementation` value computed in `views/` (none / recipe / measured / healthchecked).
- The maintainer:
  - Implementation results should be collected in the recipe readme as far as possible. Ideally every dataset is trained properly, the readme reports the results, and the DB cites the readme.
  - **The DB creates no information; everything in it refers to some source, and it is only the hub that connects them.** It may be more a hub than a database.
  - The "health check" is not a concept that should exist. It should go, or be treated as purely local information.
  - The aim is to move towards the ideal state gradually over the coming months. Data amounts will stay; only the results will be rewritten.
- Claude:
  - The exception today: `measurements/<recipe>.json` is produced by the DB's own `tools/measure.py`, which reads the ESPnet outputs (`$<CORPUS>_OUTPUT/manifest/*.tsv`) and the audio. The DB measures by itself. As a hub, this would be the recipe side's job.
  - The `exp/` directory of one recipe (emotiontalk) was inspected. It has `inference/metrics.json` (WA, UA, Macro-F1, mAP, AUC), per-utterance `ref.scp` and `hyp.scp`, `speech_shape`, and the training log. It lacks counts per label (those are in `$OUTPUT/manifest`), provenance, license and listening notes.
  - `exp/` is local and large, so readers of a public DB could not check it.
- The maintainer's conclusion:
  - `exp/` and manifests are not part of the ESPnet pull request and cannot be cited. The readme should be treated as authoritative; the DB takes facts from it as correct, and in exchange the readme must state everything needed, correctly.
  - A script writing tables from `exp/` into the readme cannot be added to the recipe, because ESPnet has no such concept and reviewers of the pull request would not understand it. To be discussed in the recipe sessions.
  - When a readme lacks a needed field in the agreed form, DB updates should warn. Reading readmes may be done by Claude rather than a strict parser, which is more flexible.
  - Short runs go into the readme with their epoch count stated, and are replaced after full training (the recipe sessions' job).

## 6. The investigation axis

- "Investigation" fits better than "review": one kind checks what published papers and pages say (literature), the other implements the recipe and learns from the result (implementation).
- Claude: a **stage** is an ordered progression; a **status** is any state.
- The maintainer: the difference is clear; write it in the manual and use a stage. The literature check is always done; if the implementation check comes first, the literature check is added afterwards.
- Candidate names (Claude): `listed` / `documents_checked` / `data_checked`; `none` / `literature` / `implementation`; `unreviewed` / `desk_reviewed` / `hands_on_reviewed`; `listed` / `surveyed` / `examined`.
- The maintainer: the first set fits best, but the third value should say "implementation check". This DB depends heavily on ESPnet: the implementation check means implementing in ESPnet and training, and finding problems that appear only then (clips so long that they harm training, chance-level results even after proper training). Does `data_checked` cover that?
- Claude: no; it reads as downloading and looking at files. Proposed `listed` / `documents_checked` / `implementation_checked`; `recipe_checked` also possible but weaker on the training part.
- The maintainer: agreed on `implementation_checked`. `recipe_checked` was not bad, but `implementation_checked` is understood at once from the value alone. This naming discussion is closed (agenda R-3).

## 7. The readme as the source

- Claude: the readme goes into the upstream pull request, so listening notes, use decisions and pending confirmations might not belong there; errors in the readme would flow straight into the DB.
- The maintainer:
  - The readme's advantage is that people can check it easily. The price is a rule that everything needed must be written in it.
  - Findings that come mainly from human judgement during the implementation check are best written in natural language, so the readme suits them.
  - **Listening notes belong in the readme.** They should be shared, and now that reading through AI is normal, a longer readme is no real problem.
  - The chance of errors in the readme must be pushed as low as possible.
  - More discussion is needed; other possibilities are to be looked at before deciding.

## 8. Dataset status

- Claude: without implementation and use decisions, what remains is whether a dataset is usable by its nature: usable / unusable / unknown.
- The maintainer: something like "conditional" is needed between usable and unusable. Features-only data or redistributions may be usable for some people or experiments. Whether a dataset is used in this experiment and whether it is usable in general must be kept apart. Audio with broken labels can still serve self-supervised learning, so no clear line can be drawn; perhaps there should be no such column.
- Claude: drop the dataset-level verdict and keep only the facts (audio availability, label properties, access terms) and reason codes for caveats. If a verdict stays: usable / conditional / unusable, with unusable only when no audio can be obtained.
- The maintainer: better not to create such columns lightly. First, the problems are endless, and a column for every state would grow the table without end. Second, a status invites people to filter datasets without looking at the primary sources. Some things deserve explicit columns and some do not; drawing the line needs careful discussion. Whether to use a dataset in an experiment is for the person who has looked at everything. To be discussed further.

## 9. Use decisions

- The maintainer:
  - This is the least stable part; it changes irregularly with the experiment, and may be what most needs to leave the DB.
  - Even now, hardly any explicit decision has been made for individual datasets.
  - The DB's rule is to always give a source, but here it cannot be given (it is unclear whether a person or an AI decided), so it does not fit.
  - Whether data is used for training or evaluation also changes quickly; it should be managed apart from the repository and not be in git.
  - It can only be decided after an implementation check, so it cannot be assigned to every dataset.
  - Ideally it is tied to an experiment ID, with the state in that experiment.
  - A place is needed for "waiting for the license" or "checked, but on hold".
- Claude: a `dataset_use.csv` with columns listed in agenda F-1; a required `decided_by` answers who decided.
- Location: the DB session manages this repository, so a git-ignored `local/` folder inside it, with the pre-commit hook refusing tracked files there. The maintainer: fine for now.

## 11. Other outcomes

- The Japanese translation of the manual is in `docs/manual.ja.md` and is always updated with the English one (commit d6264c9).
- The discussion notes are kept in the repository (`docs/design/`), because how the DB was designed matters to everyone who uses it.
- The maintainer pointed out that the three main conclusions of the day were not yet decisions but open questions: should the readme be the authoritative source, should investigation be a stage with the literature check required, should use decisions live in `local/dataset_use.csv`. A discussion counts as finished only when the question's background, the final decision and a clear, logical reason are written together.
