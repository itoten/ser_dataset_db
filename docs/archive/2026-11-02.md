# Discussion record: 2026-11-02 and 2026-11-03

The implementation of the redesign, and the decisions that came with it. Each item: question, background, decision, reason. The first part adds decisions of 2026-11-01 that the record of that day does not contain.

## Settled on 2026-11-01, added here

### Special data

- **Question.** How should data such as a corpus of non-verbal vocalizations by minimally speaking people be treated?
- **Decision.** The DB records facts only. A trait of the speakers (children, a speech impairment, a particular group) is recorded as sourced text when the source states it. Whether a dataset is "special" and whether to use it are the user's decisions and live in `local/`.
- **Reason.** Both depend on a research purpose; recording them publicly breaks neutrality.

### Total duration of a release

- **Question.** Should the DB hold a measured total duration (`hours_measured`)?
- **Decision.** No. The DB counts and measures nothing. `hours_reported` is what the documentation says; `hours_release` comes from the recipe readme.
- **Reason.** A number computed by the DB's own script would be a fact without an outside source (see 2026-10-31, A-1).

### Order and conditions of the implementation

- **Decision.** Change the form first (P0 to P8: remove columns and tables, shape the evidence rows, the list of sources, the label sets, the import of the 102 recipe readmes, views, documents and the maintenance skill), then investigate (P9), then ask a person to check (P10). The removed tables are first copied into the git-ignored `local/`. The per-label counts of a recipe move to `label_counts` from the readme. The traces of the original spreadsheet are removed (they have no source; git history keeps them). Titles, the reason a source is about the dataset, and archive links are filled during the investigation, not during the migration. Public web pages may be saved to the Internet Archive for link rot (only public URLs are sent). The manuals are rewritten last. The work runs without stopping; only a problem the plan does not cover stops it.
- **Reason.** Investigating on the old form would have to be redone. Rewriting documents last avoids rewriting them twice.

### Evidence for the attributes of a label set

- **Question.** One source per annotation row, or one per value?
- **Decision.** Per value: the evidence field is `<item>.<attribute>` (for example `emotion_categories.label_basis`), so that annotator, basis and verification each have their own source.
- **Reason.** The three attributes are often stated in different places.

## Decisions of 2026-11-02 and 2026-11-03

### One basis per label set

- **Question.** A label set had values such as `intended;perceived`. Is that one set or two?
- **Background.** In some releases the label is the emotion the actor was asked to portray, and listeners' judgements are a separate set of data; in others one label field mixes bases.
- **Decision.** A set has one `label_basis`. When a release has separate labels of another basis, they are a further annotation row named `<basis>_<item>` (for example `perceived_emotion_categories`) with its own annotator, basis and verification. Listeners' ratings that are not category labels stay `listener_ratings` rows. Where one label field mixes two bases and nothing separates them, the two values stay on that set (two datasets today).
- **Reason.** Annotator, basis and verification differ between the two kinds of label; one cell for both cannot say which is which.

### A person's check is recorded only through a pull request

- **Question.** Which rows may carry `checked_by=user`?
- **Background.** Twenty-five rows carried it because a chat or a review had once said the maintainer looked; no public record showed it. Earlier, rows that were already marked were kept as they were.
- **Decision.** `checked_by=user` is set only by a verification pull request that the maintainer merges; the note carries the pull request number, and the validator rejects any other `user` row. The 25 rows went back to `claude`. This reverses the earlier decision to keep the old marks.
- **Reason.** A record that nobody can inspect is not a record. A pull request stays public and shows who merged what.

### What the license pull requests cover

- **Decision.** Every `license_spdx` row of the datasets with a recipe, including `none_stated`, `unknown` and `conflicting` values. For a `conflicting` license the person checks that each statement exists; the value stays `conflicting`. A row whose source had no URL (a copy bundled in a download) is checked at the same paper online.
- **Reason.** A missing or disputed license is also something a reader relies on. The DB does not choose between disagreeing sources.

### Values whose source could not be opened

- **Decision.** Values resting only on a survey or mirror, whose real source Claude could not open, go to the maintainer in separate browser-check pull requests. Merging replaces the survey row with a row citing the opened page and marks it as checked by the person.
- **Reason.** The check needs a browser; the record is the same pull request mechanism.

### `unknown` means the document was read

- **Question.** When may a cell say `unknown` or `none_stated`?
- **Background.** About 360 such values had been set by searching the text of a source for the field, and many rested on an abstract or on a page that was only a script shell.
- **Decision.** Only after the whole document was read and it does not say. Anything less leaves the cell empty (unchecked). The 363 search-based values were withdrawn.
- **Reason.** `unknown` claims a thorough check that did not happen; an empty cell claims nothing.

### Sentences in free text

- **Decision.** Every sentence of `notes`, `license_note`, `language_note` and `source_rights_note` ends with `[source_id]` of an existing source; a sentence no source supports is removed; the validator checks this.
- **Reason.** Free text was the last place where a fact could stand without a source.

### Other forms

- `official_split` is a boolean: `true` or `false` only where a source says so, otherwise empty.
- A duration given in minutes is stored in hours and the note says so.
- A source's `identity_basis` says why it is about the dataset; a source that cannot be tied to the dataset's authors is marked `secondary`.

### A dataset nobody can trace is removed

- **Question.** What is a dataset for which no document names it?
- **Background.** Three entries (`dzafic`, `kite`, `egyptian_hf_unresolved`) came only from an internal working note that listed candidates by short names. Searching found that `dzafic` is the surname of the author of a University of Queensland video set that the DB already holds as `uq_schizophrenia_videos` (a public list of corpora cites it that way); nothing could be found for the other two.
- **Decision.** `dzafic` is merged into `uq_schizophrenia_videos` as an alias whose source is that list. `kite` and `egyptian_hf_unresolved` are removed, with their evidence rows and aliases. The validator now rejects a dataset that has no linked source with a URL, and an evidence row whose source is not linked to its dataset.
- **Reason.** A name that no reader can find in any document may be an error or an invention, and nobody, including the DB's maintainer, can verify it. Verifiability applies to the existence of a dataset as much as to its values.

### Names come from what a source prints

- **Decision (2026-11-03).** A dataset's `name` is a name that one of its sources prints: a short name in the title or text, a catalogue's name field (as a `secondary` source), a repository name, or else the title of the paper or page. A name the DB made up is not kept.
- **Found on the way.** `eekk` and `eesc` were two entries of the same Estonian corpus (an existing relation already said so); `eekk` is merged into `eesc` as an alias.

## What `provisional` means, and why it must go

- **What it is.** A `provisional` evidence row is a value without a public source. It exists only because an earlier version of the DB held the value (a short name, an observation that a download worked, a value from an internal note) and the migration kept it until a source could be found.
- **Decision (2026-11-03).** This is a transitional state, not a final one. Every value in the DB must have a source: the primary source if one can be opened; if the value is only listed by a survey or catalogue, that listing, kept as a `secondary` source. A value that has no source of either kind is removed (the cell is left empty). A value that came from an internal note is never a source.
- **Reason.** The DB creates no facts of its own. A value no reader can trace to a document breaks verifiability, however it got there.
- **Work.** The remaining `provisional` rows are to be resolved one of three ways: find the source (primary, else the listing that named it), replace the value by what a source prints, or remove it.

## Process notes

- Matching sentences against cached copies of the recipe readmes dropped every sentence that came only from a readme, because the cached copies were empty page shells. The check should read the real text of the source it matches against.
- Pull requests that touch neighbouring lines of the same file conflict. The verification batches now keep a gap between them and are rebuilt from the current main whenever it changes.
