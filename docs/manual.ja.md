### 1.3 何が役に立つか

- **すべての値に出典がある**: 「ライセンスは CC-BY-4.0」と書くだけでなく、どの文書のどの箇所を、いつ、誰が確認したかを 1 行ずつ記録している。
- **推測しない**: 分からないことは「分からない」と記録する(7)。URL やタイトルを作り上げることはしない。
- **食い違いが見える**: 2 つの出典が食い違うときは両方を残し、値は `conflicting` になる。DB はどちらかを選ばない。
- **機械が検査する**: `validate.py` が形式・出典・根拠を自動で検査し、通らないコミットは拒否される。
- **実装で分かったリリースの事実**: 各リリースのファイル数・話者数・時間、ラベルごとの本数、ESPnet のレシピ(実験の設定一式)を作る中で見つかった問題を、recipe の readme から写している。

## 2. なぜ作ったか

### 2.1 背景

深層学習を中心とした今の AI 研究では、データの規模を無視できない。複数のデータセットを統合して使うマルチコーパス研究も、重要な手法になっている。そのため研究者は、より大きなデータセット、より多くのデータセットを探し続けなければならない。

しかし、データセットは日々新しく作られ、再配布され、使えなくなっていく。情報の移り変わりが速いため、誰かが作ったデータセット一覧は数年で役に立たなくなり、そこに書かれた情報が正しいかどうかも、結局は自分で確かめ直さなければならない。その結果、研究者が追うべき情報は膨れ上がり、データセットを調べること自体のコストが肥大化している。

近年の AI の発展により、AI を使えば検索エンジンより網羅的に情報を探せるようになった。しかし、研究者が新しい研究を始めるたびにそれぞれ調べていては、皆が同じ情報を得るために同じ手間とトークンを使い続けることになる。

だからこそ、世界中のデータセットの最新情報に簡単に辿り着くための三次資料、いわば「データセットの Wikipedia」が求められている。

### 2.2 課題

1. **協力者なしに網羅すること。** Wikipedia の網羅性は、大勢の人の協力によって成り立っている。しかし、SER のような狭い研究分野では、そうした協力は期待できない。少ない人手で、できるだけ多くのデータセットとその情報を集めなければならない。
2. **変わり続ける情報に追いつくこと。** データセットは新しく生まれ、再配布され、消えていく。ライセンスなどの条件も、作者の都合で変わることがある。一度集めた情報もすぐに古くなるが、多くの一覧では、その情報がいつの時点のものかすら分からない。
3. **正しさを保証できないこと。** 誰が調べても誤りは起こる。人も間違えるし、AI はハルシネーションを起こす。どれだけ注意しても、「絶対に正しい情報」を提供することはできない。しかも既存の一覧の多くは出典を示さないため、利用者は誤りに気づけず、結局すべてを自分で調べ直すことになる。

### 2.3 理念

研究者がデータセットを調べるコストを下げるために、SER 研究に使えるデータセットの最新情報を網羅的に集め、誰もがその一次資料を確かめられるデータベースを提供する。

### 2.4 原則

原則のあいだに優先順位はない。

| 原則 | 内容 |
|---|---|
| **検証可能性** | すべての値は、誰でも一次資料で確かめられる。この DB が提供するのは「真実」ではなく、真実に辿り着くための「道」である。出典のない情報は載せない。利用者には、必ず一次資料を確かめるよう勧める。 |
| **網羅性** | できるだけ多くのデータセットと、その情報を集める。一度の調査で取りこぼした情報も、繰り返しの調査や人からの情報提供で補い、どこよりも網羅的な情報を目指す。 |
| **最新性** | 新しい情報を取り込み続け、古い情報を確かめ直す。すべての情報に確かめた時期を記し、利用者がその情報の新しさを判断できるようにする。 |
| **透明性** | 誰が、いつ、何を確かめたかを明らかにする。特に、人が検証した情報か、AI が調べただけの情報かを区別する。同じ DB の中でも情報の確からしさには差があり、それが見えなければ、利用者はどの情報をどれだけ信頼してよいか判断できないからである。分からないことや、DB の限界も明記する。 |
| **中立性** | 事実だけを記し、「使うべきか」「良いデータか」といった判断は提供しない。データセットが使えるかどうかは研究の目的によって変わるうえ、判断が書かれていると、利用者は一次資料を見ずにそれに従ってしまうからである。情報が食い違うときも、どちらを信頼すべきかは決めず、判断を利用者に委ねる。 |

これらの原則が、規則(このマニュアル、`schema/`、`tools/validate.py`)と手順(メンテナンス用の skill)の土台になる。原則から決まったことは、理由とともに [design/](design/agenda.md) に記録している。

### 2.5 手法

データセットの情報は、ほとんどが Web 上にあり、誰でもアクセスできる(論文、配布ページ、ライセンスのファイルなど)。そのため、一次資料への道を正確に書くことができる。道を作る作業は AI に任せられ、確かめる人は道ではなく、行き着いた先の出典だけを見ればよい。これにより、少ない人手でも網羅性と検証可能性を両立できる。主な手法は次の 4 つである。

| 手法 | 内容 |
|---|---|
| **値ごとの根拠** | 値 1 つごとに、出典の文書、その中の該当箇所、確かめた日付を記録する。 |
| **検証状態の明示** | 各値について、AI が調べただけか人が確かめたか(`checked_by`)、そして公開の出典があるか(`provisional` でないか)を記録する。 |
| **継続的な再検証** | 根拠と値が合っているか、出典が今も同じことを述べているかを、定期的に確かめ直す。 |
| **AI に適した設計** | 調査・検証・閲覧に AI を使うことを前提にする。人にとっての読みやすさのために情報を削らない。生成される view は補助で、主な読み方ではない。 |

### 2.6 利用者へ

- 値に頼る前に一次資料を確かめ、引用するときはこの DB ではなく一次資料を引用する。
- データセットを使ってよいかは、一次資料をもとに利用者自身が判断する。DB は法的助言ではない。
- 自分の目的に依存する判断(どのデータセットを使うか、ライセンスやラベルをどうまとめるか)は利用者のもの。git で無視される `local/` に置く(12.3)。

## 3. 用語集

### 3.1 研究の用語

| 用語 | やさしい説明 |
|---|---|
| **SER**(音声感情認識) | 声から感情(怒り・喜び・悲しみなど)を機械に認識させること |
| **コーパス / データセット** | 研究用に整理した音声データの集まり。ここでは同じ意味で使う |
| **ラベル** | 録音に付けられた「答え」。例: 「angry」 |
| **カテゴリ感情** | 感情を、怒り・喜びのような少数の箱のどれかで表すこと(ラベルの組 `emotion_categories`) |
| **次元感情** | 感情を数値、典型的には valence(快‐不快)と arousal(覚醒度)で表すこと(ラベルの組 `emotion_attributes`) |
| **発話(utterance)** | ひとまとまりの音声。データ量はファイル数または発話数で数える |
| **演技 / 即興 / 誘発 / 自然発話 / 朗読** | 声の出し方: 指示された感情で演じた/台本なしで演じた/課題や刺激で引き出した/自然な発話/感情の指示なしに読んだ |
| **意図 / 対話行為** | 感情ではなく、話者がしたかったこと(「アラームをセットして」)や発話の機能(質問・依頼・同意)。DB は感情以外のパラ言語情報も扱うので含めている |
| **パラ言語情報** | 言葉以外に声が運ぶ情報(感情・話し方・意図・センチメントなど) |
| **センチメント(極性)** | 感情の向き。ポジティブ/ネガティブなど |
| **TTS / ASR** | 音声合成 / 音声認識。TTS 用に録られた感情コーパスは含め、ASR 専用のデータは対象外 |
| **聴取評価** | 人が録音を聴いて、たとえばどの感情に聞こえるかを答える評価 |

### 3.2 ESPnet の用語

| 用語 | やさしい説明 |
|---|---|
| **ESPnet / ESPnet3** | 音声処理のオープンソース研究ソフトウェア。このプロジェクトが SER を追加している |
| **レシピ(recipe)** | 1 つのデータセットで学習・評価するための設定一式。フォルダ `egs3/<name>/cls` |
| **recipe の readme** | レシピの `readme.md`。その `## The data` 節は、配布されたままのリリース全体について recipe の作者が書いたもので、DB がリリースの数を引用する先 |

### 3.3 データ管理の用語

| 用語 | やさしい説明 |
|---|---|
| **CSV** | カンマ区切りの表ファイル。Excel・Google スプレッドシート・LibreOffice で開ける |
| **正(authoritative)のデータ** | 原本と宣言したデータ: `data/*.csv`。`views/` はそこから生成されるので、`views/` を直接編集しない |
| **git / コミット** | ファイル変更の履歴を記録するソフトウェアと、記録された 1 回の変更。いつ何が変わったかを後で見られ、戻すこともできる |
| **プルリクエスト** | GitHub 上で、誰かが確認して取り込む変更の提案。ここでは maintainer が値を確かめたことの記録に使う |
| **フック** | コミットの直前に自動で走る検査。通らないとコミットが拒否される |
| **キー(ID)** | 行を特定する名前。例: `dataset_id`(`ravdess`)。一度決めたら変えない |
| **外部キー** | 別の表のキーを指す列。例: `evidence.dataset_id` は `datasets` の行を指す |
| **スキーマ** | 設計: 列名・型・意味。`schema/` にある |
| **導出列** | 他の表から `tools/derive.py` が計算する列。手で編集しない |

### 3.4 出典の用語

| 用語 | やさしい説明 |
|---|---|
| **一次資料(primary)** | データセットの作者またはその組織が公開したもの(論文・公式の配布ページ・LICENSE ファイル・リリースのファイル) |
| **実装の出典(implementation)** | recipe の readme の `## The data` 節。recipe の作者がリリースをダウンロードして開いたあとに書いたもの。実用上の参考で、研究の成果ではない |
| **二次資料(secondary)** | 他の人が書いたもの(まとめサイト・再アップロードのページ・サーベイ)。一次資料にアクセスできないときだけ使う |
| **provisional(仮の値)** | 以前の記録から引き継いだ、公開の出典がまだない値 |
| **Hugging Face(HF)/ Kaggle / Zenodo / figshare / Mendeley Data** | データセットが公開されているサービス |
| **DOI** | 論文やデータの恒久的な識別子 |
| **ISO 639-3** | 3 文字の言語コード: `eng` 英語、`jpn` 日本語、`cmn` 中国語(北京官話)、`mul` 内訳のない複数言語、`zxx` 言語内容なし |

### 3.5 ライセンスの用語

ライセンスは、データをどこまで使ってよいかを定めたもの。ここでの説明は一般的なもので、法的助言ではない。

| 用語 | やさしい説明 |
|---|---|
| **CC(クリエイティブ・コモンズ)** | 利用条件を決まった記号で表す仕組み |
| **BY / NC / SA / ND** | 作者のクレジットを表示すれば使える / 非商用のみ / 派生物も同じ条件で共有 / 改変禁止 |
| **CC0** | 権利放棄。自由に使える |
| **MIT / Apache-2.0 / GPL** | ソフトウェアのライセンス: 寛容(クレジット)/ 特許条項つきで寛容 / 同じ条件での共有を強く求める |
| **SPDX 識別子** | ライセンスの公式な短い名前(例: `CC-BY-4.0`)。表記ゆれを避けるために使う |
| **LicenseRef-...** | SPDX にない独自条件に付ける、この DB 独自の名前(10) |
| **再配布** | 受け取ったデータを他の人に渡したり、別の場所で公開したりすること。許されないことが多い |

## 4. DB には何があるか

### 4.1 フォルダの地図

| 場所 | 内容 |
|---|---|
| `data/` | 正の表(CSV) |
| `views/` | `data/` から生成: `datasets_wide.csv`(1 データセット 1 行)、`discrepancies.csv` |
| `schema/` | 定義: `columns.csv`、`enums.csv`、`tables.csv` |
| `tools/` | 検査・編集のツール(`validate.py`、`derive.py`、`views.py`、`db.py`) |
| `docs/` | このガイド(英語と日本語)と、`docs/design/` の設計の記録 |
| `local/` | 各自の作業用の場所。README 以外は git で無視される |
| `.claude/skills/` | Claude Code で DB を保守する手順 |

### 4.2 表(`data/`)

| ファイル | 1 行は |
|---|---|
| `datasets.csv` | 1 つのデータセット |
| `evidence.csv` | 1 つの値の根拠 |
| `sources.csv` | 1 つの出典の文書 |
| `dataset_sources.csv` | データセットを紹介する出典(論文・配布・カード・ミラー・readme) |
| `annotations.csv` | データセットのラベルの組、またはほかのアノテーション |
| `label_counts.csv` | ラベルの組の、出典が述べるラベルごとのファイル数 |
| `issues.csv` | 配布されたままのリリースの問題 1 件 |
| `aliases.csv` | データセットの別名 |
| `relations.csv` | データセット間の関係(版・部分集合・別物・同一の疑い・共有する文) |
| `label_normalization.csv` | ラベル名の表記ゆれ・語形の違いと、その正規化した形 |

### 4.3 表のつながり

`datasets` が中心。`evidence`・`annotations`・`label_counts`・`issues`・`aliases`・`relations`・`dataset_sources` は、データセットの `dataset_id` を持つ。`evidence`・`annotations`・`label_counts`・`issues`・`aliases`・`relations`・`dataset_sources` は、`source_id` で `sources` の文書を指す。

### 4.4 1 行とは何か

元の(最初に公開された)データセット 1 つにつき 1 行。単なる再アップロードは行にせず、別名とミラーの出典にする。内容が元と違うデータセット(再分割・部分集合・新しいラベル)は別の行にして `relations` で結ぶ。作者が別の名前や DOI で公開した版は別の行(`version_of`)、それ以外の版は同じ行で、出典ごとの `describes_version` がどの版について述べているかを示す。

## 5. `datasets` 表の読み方

### 5.1 まず見る列

| 列 | 意味 | 例 |
|---|---|---|
| `name`、`full_title`、`languages` | 名前、題名、ISO 639-3 のコード | `RAVDESS` / `eng` |
| `license_spdx` | 述べられた条件を SPDX 識別子で表したもの(10) | `CC-BY-NC-SA-4.0` |
| `access_method` / `access_observed` | 資料が述べる入手のしかた / 実際に申請・ダウンロードしたときに起きたこと | `request_form_or_email` / `obtained` |
| `n_files_reported`、`hours_reported`、`n_speakers_reported` | 資料が述べる値 | `1440` |
| `n_files_release`、`hours_release`、`n_speakers_release` | 配布されたままのリリース全体の値。フィルタ前(recipe の readme) | `1440` |
| `speech_production`、`material_origin`、`vocal_content` | 声の出し方、音声の出どころ、話し声か非言語か | `acted` / `recorded_for_dataset` / `speech` |
| `spoken_text_design` | 話す文とラベルの関係 | `parallel` |
| `emotion_categories`、`emotion_attributes`、`main_label_set_type`、`main_labels`、`label_source`、`label_basis`、`label_verification` | 主なラベルの組と、その作り方(`annotations.csv` から導出) | `angry;happy;sad` / `human` / `intended` |
| `official_split`、`listening_test` | 公式の分割がある。聴取評価が報告されている | `false` / `reported` |

### 5.2 資料とリリースの違い

資料(論文・ページ)と配布されたリリースは、版・丸め・作者が除いたファイルなどで食い違うことが多い。両方を並べて記録し(`*_reported` と `*_release`、`access_method` と `access_observed`)、DB はどちらかを選ばない。レシピ自身のフィルタや分割のあとの数は記録しない。

### 5.3 注記の列

`notes`・`language_note`・`license_note`・`source_rights_note` は自由記述。事実と注意点だけを書き、文ごとに出典を括弧で示す(`[aesdd_page]`)。`license_note` は識別子だけでは条件が伝わらないときだけ使い、`source_rights_note` は第三者の素材の権利について出典が述べることを引用する。DB は判定を書かない。

### 5.4 ラベルの組

ラベルの組は、`item` が `name` と同じ `annotations.csv` の行: `emotion_categories`、`emotion_attributes`、`speaking_style`、`sentiment`、`intent`。出典の言葉のままの `labels`、出典が述べる粒度 `scale`、`perceived_from`(聴いた人が何を見聞きしたか)と、それぞれ自分の根拠の行を持つ 3 つの属性がある。

| 属性 | 値 |
|---|---|
| `annotator` | `human`、`automatic`、`mixed`、`synthesis_specified`(合成音声で、合成器に与えた感情をラベルにしたもの) |
| `label_basis` | `intended`(話者が演じるよう指示された感情)、`perceived`(聴いた人が知覚した感情)、`self_reported`、`context_inferred`(場面・台本・言葉の意味から)、`automatic` |
| `label_verification` | `human_reviewed`、`listener_validated`(指示されたラベルを聴取評価で確かめた)、`none`、`unknown`、`NA` |

ある属性から別の属性を推測してはいけない。演技の音声にも知覚ラベルが付くことがある。1 つのデータセットに複数のラベルの組があることもある(指示された感情と知覚された感情、カテゴリと次元、感情と話し方)。datasets の列には主なものが出る。

### 5.5 ラベルごとの本数

`label_counts.csv` は、ラベルの組の各ラベルのファイル数を、出典の言葉のラベルで持つ。論文の表と recipe の readme が同じラベルの数を述べることがあり、一致するとは限らないので両方を残す。`label_normalization.csv` が対応づけるのは表記(大文字小文字・空白)と語形(angry/anger)だけ。意味を変える対応づけ(joy を happy にするなど)はプロジェクトの判断で、DB には置かない。

### 5.6 ほかのアノテーション

書き起こし・話者の属性・評定などは、固定の語彙の `item`(`speaker_id`、`speaker_gender`、`transcript`、`sentence_id`、`session_id`、`take`、`intensity`、`listener_ratings`、`listening_test`、`segmentation`、`acoustic_features`、`split`、`video`、`physiological`、`other`)と、リリース自身の呼び名の `name` を持つ `annotations.csv` の行。各行が自分の出典を持つ。

### 5.7 聴取評価

`listening_test` が示すのは、人による聴取評価があること(`reported`)、または読んだ出典が何も述べていないこと(`not_stated`)だけ。結果や設計(聴いた人・選択肢・映像を見せたか)は評価ごとに違い、データセット間で比べられないので、出典に残す。リリースが評定を配布していれば `listener_ratings` のアノテーションになる。

### 5.8 リリースの問題

`issues.csv` は、リリースを開いたときに見つかったことを並べる: 壊れた・空のファイル、重複、ラベルの欠けや不一致、資料との違い、無音・音声でないファイル、変わった音声、聴いた観察。1 行が 1 つの問題で、recipe の作者の言葉のまま、分かればファイル数と readme の場所を添える。聴いた観察は作者の観察(「Observation by the recipe author (日付)」)で、測定ではない。

### 5.9 列の定義

`schema/columns.csv` が全列を定義し(型・許される欠損値・根拠を取るか)、`schema/enums.csv` が許される値とその意味を並べる。

## 6. 出典と根拠

### 6.1 なぜ根拠を残すか

出典のない値は確かめられず、確かめられない一覧は信頼されない。根拠を取る列の値には、`evidence.csv` に少なくとも 1 行がある。

### 6.2 出典と根拠の行に何があるか

**出典**(`sources.csv`)は文書: URL か DOI、題名、`kind`(paper、distribution_page、dataset_card、license_file、release_files、readme、mirror、survey、other)、`publisher`(authors、third_party、recipe_author)、`source_type`(primary、secondary、implementation)、それが述べるデータセットの版、なぜこのデータセットの文書と言えるか、確かめた日。公開元が空の出典はまだ確かめていない出典で、validate が一覧にする。同じ文書が、あるデータセットでは一次資料、別のデータセットでは二次資料になることがあり、その場合は 2 つの出典になる。

**根拠の行**(`evidence.csv`)は、「この項目のこの値は、この出典の、この箇所(`locator`)に書かれていて、この日に、`claude`(AI の調査)または `user`(maintainer が出典を開いた)が確かめた」と述べ、`status` を持つ。

### 6.3 値の決まり方

| 項目の行 | セルの値 |
|---|---|
| `current` の行がすべて同じ値 | その値 |
| 値の違う `conflicting` の行が 2 つ以上 | `conflicting` |
| `provisional` の行が 1 つ | その値(公開の出典はまだない) |

値が置き換わったとき、古い行は `superseded` にして残す。履歴は消さない。

### 6.4 recipe の readme の位置づけ

recipe の readme を引用するのは、資料が述べておらず、リリースを開いて初めて分かることだけ: リリースの数、重複、ファイルの中身。公開フォークのコミットで引用し、`locator` は `commit <ハッシュ>; <見出し>` とする。論文やページが同じことを述べていれば、readme が繰り返していても、その出典を引用する。

### 6.5 仮の値

`provisional` の行は、以前の記録から引き継いだ、公開の出典がない値: 名前・題名や、かつて内部のメモや DB 自身の測定から入った値。そのように表示され、出典を確かめ次第、置き換える。

### 6.6 人による検証

maintainer は値をまとめて(20 行ほど、まずライセンス)`verify/<日付>-<番号>` のプルリクエストで確かめる: リンクを開き、引用された言葉を見比べ、マージする。マージされたプルリクエストの行は `checked_by=user` になる。

## 7. 欠損値の書き方

| 書き方 | 意味 |
|---|---|
| (空) | まだ確認していない |
| `unknown` | 確認したが、資料が述べていない、または決められない |
| `NA` | 当てはまらない |
| `none` | 確認した結果、ない |
| `conflicting` | 資料が食い違う |

列がどれを受け付けるかは `schema/columns.csv` の `nulls` 列にある。複数の値は `;` で区切る。

## 8. 導出列

`datasets.csv` の `emotion_categories`・`emotion_attributes`・`main_label_set_type`・`main_labels`・`label_source`・`label_basis`・`label_verification` は、主なラベルの組から `python3 tools/derive.py` が計算する。異なると validate が失敗する。主な組は、`emotion_categories`、なければ `emotion_attributes`、なければほかのラベルの組。

## 9. 入手

`access_method` は資料が述べること: `direct_download`、`free_account_required`、`gated_click_through`、`request_form_or_email`、`signed_agreement`、`paid_or_membership`、`unofficial_mirror_only`、`unavailable`、`unknown`。`access_observed` は、実際に申請・ダウンロードしたときに起きたこと(`obtained`、またはそれらの値)で、`access_observed_on` がその日付。入手が難しいデータセットや、音声が配布されていないデータセットもある。DB はそれを記録するが、それでデータセットに順位は付けない。

## 10. ライセンス

### 10.1 2 つの列

`license_spdx` は述べられた条件を SPDX 識別子で表したもの。`license_note` は、識別子では言えないこと(独自のライセンスの要点)を言う。どちらもデータのライセンスについてで、背後の第三者の素材の権利(`material_origin`、`source_rights_note`)ではない。

### 10.2 独自の条件

SPDX にない条件は、`LicenseRef-custom-research-only`(研究用のみ)、`LicenseRef-proprietary-restricted`(制限つきまたは有償)、`LicenseRef-citation-request`(引用の依頼だけ)、`LicenseRef-other`、`none_stated`(記述が見つからない)。`conflicting` は資料が食い違うこと。

### 10.3 データセットを使う前に

識別子は文言の分類で、法的助言ではない。一次資料を開いて条件を読み、データのライセンスと同梱コードのライセンスが違わないかを確かめる。実験のためにライセンスをどうまとめるかは利用者自身の判断(12.3)。

## 11. 検査

`tools/validate.py` は、形式・型と許される値、キーと外部キー、出典と根拠の規則、導出列、名前の重複、`views/` が最新か、マシン固有のパスがコミットされていないか、を検査する。コミット前のフックが実行する。迂回しない。

## 12. DB の使い方

### 12.1 調べる

1. `views/datasets_wide.csv` を表計算ソフトで開いて絞り込む(たとえば `license_spdx`、`languages`、`main_label_set_type`)。
2. 頼る値は、`data/evidence.csv` の行(`dataset_id` と `field`)を調べ、`data/sources.csv` の出典を開く。
3. `views/discrepancies.csv` は、出典が食い違う値を並べる。

### 12.2 AI のために

DB は AI を通して読まれることを想定している。まず `README.md` を読み、必要な行を読む。一次資料を示して答え、根拠が仮の値・二次資料・実装の出典のときはそう伝え、空・`unknown`・`conflicting`・仮の値のときだけ外を調べる。

### 12.3 `local/`

`local/` は git で無視される作業用の場所(その README を見る): どのデータセットを使うか、なぜか、ライセンスをどうまとめるか、ラベルをどう対応づけるか。自分のファイルは `dataset_id` で DB と結ぶ。DB のツールは `local/` を読まない。

## 13. データの追加と変更

変更はメンテナンス用の skill(`.claude/skills/maintaining-ser-dataset-db/`)で行う: 出典を登録し、値を根拠つきで登録し、`tools/views.py` と `tools/validate.py` を実行し、何が不確かで根拠が何だったかをコミットメッセージに書く。コミットしたものはすべて公開される。

## 15. 限界

### 15.1 DB がまだできていないこと

- ほとんどの値は AI の調査が根拠で、人が出典を開いたものは少ない。値に頼る前に一次資料を確かめること。
- 754 行の仮の値(名前・題名と、出典が必須になる前の値)と、公開元をまだ確かめていない 210 の出典が、残る主な作業。`views/datasets_wide.csv` に各データセットの段階が出る。
- recipe の readme は recipe の作者が書いたもので、その数は作者の数え方の確かさ次第。

### 15.2 DB がしないこと

どのデータセットを使うべきかは言わず、順位も付けず、食い違う出典のどちらかを選ぶこともしない。
