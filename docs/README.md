## 書き方の規則

- 議論と計画は日本語で書く。マニュアルと README は英語(と日本語訳)のまま。
- ファイル名は `NNNN-短い英語名.md`。番号は議論と計画で別々に、1 から順に振る。
- **ファイルの先頭に `状態:` の行を書く。終わってもファイルは動かさない**(動かすとリンクが切れる)。
  - 議論: `議論中` / `決定` / `取り下げ`
  - 計画: `計画` / `実装中` / `済み`
- **議論は、背景・決定・理由がそろったときだけ「決定」にする。** 合意や「こちらに傾いている」は決定ではない。
- 決定が DB を変えるのは、maintainer が頼んだときだけ。
- 議論が決定になったら、関連する計画を作るか更新する。計画は、元の議論の番号を書く。
- このリポジトリは公開なので、個人名、メールアドレス、手元のパスを書かない(「maintainer」と書く)。
- 作業の段階を表す内部の番号(P9 など)は使わない。初めて読む人に意味が通じる名前で書く。

## 保留と、答えの出ていない問い

以前の `agenda.md`(英語、[archive/agenda-until-2026-11-03.md](archive/agenda-until-2026-11-03.md))から引き継いだもの。

### 保留

| 項目 | 保留の理由 |
|---|---|
| 自由なタグ列 | 足すのは簡単だが、「すべての値に出典がある」と相性が悪い。`local/` でなら使えるかもしれない |
| 名前(データベースかハブか、wiki か) | いつでも変えられる |
| 持続性: maintainer がいなくても DB を運用できるか | リポジトリとメンテナンス用の skill で可能にすることを目指す |
| データセットの作者からの訂正(GitHub の issue など) | 公開してから |
| 多くの人の協力(読者が資料を確かめて報告する) | 公開してから |
| 値を資料と照らす定期的な自動確認、登録時のテスト | 構造が落ち着いてから。token の費用を見積もる |
| 古い値の検出(最後の確認からの日数) | 今はすべて新しい |

### 答えの出ていない問い

DB を保守していて、何度も出会う問い。

- 事実に専用の列を与えるか、自由記述に残すか(表が太るか、探せなくなるか)。今のところ、多くのデータセットに当てはまり、絞り込みに使うものだけ列にする。それ以外は出典つきの自由記述にして、同じことが何度も出てきたら列に上げる。
- AI が扱いやすい設計(token が限られる)。同じ調査を繰り返さない。設計を比べる物差しにする。

### 残っている開いた項目

- 仮の値(`provisional`、公開された出典のない値)を片づける。出典(一次資料、なければそれを載せたカタログ)を見つけるか、セルを空にする。[plans/0001](plans/0001-remaining-data-work.md) に進め方を書いた。
