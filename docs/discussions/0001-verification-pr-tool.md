## 1. 今の道具の問題

今は `local/`(git 管理外)にある 2 本のスクリプトで PR を作っている。

| 問題 | 中身 | 困ること |
|---|---|---|
| 1-1 名前 | `p10_make_prs.py`、`p11_make_prs.py`、ブランチ名の `2026-11-03b`。再設計の作業段階の番号 | 議論にいなかった人には意味が分からない |
| 1-2 置き場所 | git 管理外の `local/` | 他の人が使えない。消えれば終わり(実際に、必要なキャッシュを消して今は動かない) |
| 1-3 混ざった役割 | 「どの行を確かめるか選ぶ」「PR を作る」「merge 後の記録」が 1 本に入っている。選び方は作業用のキャッシュ(論文本文の写し)に頼っている | 選び方を変えるたびに全体を書き直す。キャッシュが無いと動かない |
| 1-4 コンフリクト | PR が `data/evidence.csv` と生成物の `views/datasets_wide.csv` を直接書き換える | PR 同士や、main の変更とぶつかる。行の間を空ける工夫や、PR の作り直しが要った |
| 1-5 PR 番号 | PR を作ったあと、番号を注記に入れる 2 回目のコミットをしている | 手順が複雑 |
| 1-6 種類ごとに別のスクリプト | ライセンスの確認と、ブラウザでの確認(資料を開けなかった値)で別のスクリプト | やっていることはほぼ同じ |

## 2. 案: 確認リストのファイル

### 2.1 考え方

PR では **DB の表を直接変えない**。かわりに、確かめてほしい行を並べた **確認リスト**(CSV 1 ファイル)を新しく足す。

- **リストの中身:** 1 行 = 確かめる値 1 つ。データセット、項目、値、開くページ、探す言葉を並べる。
- **merge の意味:** 「maintainer がこのリストの値を全部確かめた」という記録になる。
- **DB への反映:** merge のあと、main で道具が `checked_by=user` を書き込む。

### 2.2 よくなること

- **コンフリクトが起きない。** PR は新しいファイルを足すだけで、他のファイルを触らない(1-4 が消える)。
- **確認する人が読みやすい。** PR の差分は、確かめる表そのものになる。GitHub は CSV を表として表示する。今の PR は、evidence の注記の書き換えと、生成物の差分が混ざっている。
- **PR 番号は merge の記録から取れる。** 2 回目のコミットが要らない(1-5 が消える)。
- **確認した値がファイルに残る。** merge までの間に DB の値が変わったときは、反映で気づける。その行は反映しないで報告する。

### 2.3 確認リストの例

```
evidence_id,dataset_id,field,value,open_url,look_for,cite_source_id
emovo/license_spdx/02,emovo,license_spdx,CC-BY-NC-SA-4.0,https://...,"licensed under ...",emovo_paper
```

- `open_url` は開くページ、`look_for` はそのページで探す言葉。
- `cite_source_id` は、確かめたあとに根拠にする資料。今の資料と同じなら、`checked_by` を変えるだけでよい。
- 別の資料なら(今の「ブラウザでの確認」)、反映のときに、その資料を引いた行を新しく作る。古い行は `superseded` にする。
- こうすれば、ライセンスの確認とブラウザでの確認が同じ仕組みになる(1-6 が消える)。

## 3. 道具の形

1 本の道具 `tools/verify.py` に、3 つの手順を入れる(名前は 6-2 で決める)。

| 手順 | コマンドの例 | すること |
|---|---|---|
| 3-1 下書き | `verify.py draft --field license_spdx --has-recipe` | 条件に合う、まだ人が確かめていない行を選んで、確認リストの下書きを書く。下書きは人か Claude が手で直してよい(開くページを変える、行を外す) |
| 3-2 PR を出す | `verify.py open <下書き> --batch-size 20` | 20 行ずつに分け、ブランチ `verify/<リスト名>` に確認リストを足し、PR を開く。PR の本文には、確認の仕方とリンクつきの表を書く |
| 3-3 反映 | `verify.py apply` | merge 済みの確認リストのうち、まだ反映していないものを evidence に書き込む(`checked_by=user`、注記に PR 番号)。views を作り直し、validate を通してコミットする |

- **選び方と PR の操作を分ける(1-3 が消える)。** 選び方は 3-1 の条件だけで決まり、作業用のキャッシュには頼らない。
- **開けなかったページの扱い:** 「Claude が開けなかったページ」のように、機械では決められない選び方は、下書きを直して表す。
- **ブラウザでの確認で、まだ資料の一覧に無いページを開く場合:** そのページは先に、普段の登録の作業で `sources.csv` に足しておく。道具は資料を作らない。

## 4. 置き場所と管理

- **置き場所:**
  - 道具は `tools/verify.py`(公開リポジトリ、MIT)に置く。
  - 確認リストは `data/` の下に専用のフォルダを作って置く。表の定義は `schema/` に足す。
- **validate で確かめること:**
  - `checked_by=user` の行が、merge 済みの確認リストのどれかに載っていること。
  - 確認リストの行が、存在する evidence を指していること。
- **文書:** `docs/manual.md`(英・日)の 6.6 に、初見の人向けの手順(下書き → PR → merge → 反映)を書く。skill からは、そこを参照する。
- **名前:** 段階の番号(p9 など)や作業の日付を、名前に入れない。リスト名は `<日付>-<内容>-<番号>`(例 `2026-11-05-license-01`)で、何を確かめるリストかが分かるようにする。

## 6. 決定(2026-11-04、maintainer)

| 問い | 決定 | 理由 |
|---|---|---|
| 6-1 確認リストを DB に置くか | 置く。公開リポジトリの `data/` の下(`checked_by` の列は残し、その根拠として置く) | DB は最初から公開。人が確かめた記録は誰でも辿れるべきで、PR の差分が確認する人の見る表そのものになる |
| 6-2 名前 | Claude に任せる。2 章と 4 章の案(`tools/verify.py`、`data/verification/`、`<日付>-<内容>-<番号>`)で進める | 作業段階の番号を使わず、初見の人に意味が通じる名前にする |
| 6-3 merge 済みの #66〜#71 を確認リストに移すか | 移す | 規則が 1 つで済む。注記の PR 番号での確認をやめられる |
| 6-4 #77〜#81 | 今のまま merge を待つ。作り直さない | 先に merge されればコンフリクトの心配がない |
| 6-5 merge 済みで反映していない確認リスト | validate をエラーにする | 次のコミットで必ず気づく |
| 6-6 `local/` のスクリプト | 新しい道具ができたあとで消す | 同じ役割の物が二重にならないように |

6-1 の確認: maintainer の質問「確認リストを公開リポジトリに置くのは、もともとそうではなかったか」への答えは、リポジトリは最初から公開であり、新しいのは「確認リスト」という表を足すこと。
